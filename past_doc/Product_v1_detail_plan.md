# V1.0 核心价值验证版 - 开发技术路线

> **历史文档标记**：暂时不用本文档进行实际任务开发，仅为项目立项时的一种参考方案。当前实际开发请以根目录的 `Final_Team_Work_Division.md` 和五份 `Member_*.md` 成员任务文档为准。

## 版本目标

V1.0 的目标是让用户第一次使用时，就能感受到：
> 这个产品比普通相册、备忘录或 Notion 更适合记录收藏。

需要验证三个最核心的价值：
1. 用户是否愿意记录收藏？
2. AI 是否能降低记录成本？
3. 美观展示是否能提升用户继续使用的意愿？

## V1.1：最小收藏记录闭环

### 产品功能

- 用户可以创建收藏记录
- 用户可以上传收藏品图片
- 用户可以填写标题、分类、时间、地点和故事
- 用户可以保存记录
- 用户可以看到自己的收藏列表

### 技术路线

#### 前端技术
- **框架**：Flutter 或 React Native（跨平台移动开发）
- **状态管理**：Provider / Riverpod / Redux（用于管理收藏记录状态）
- **图片选择**：image_picker 插件（支持相册选择和相机拍摄）
- **本地存储**：SQLite（用于存储收藏记录结构化数据）
- **图片存储**：本地文件系统 + 图片压缩（减少存储压力）

#### 后端技术
- **框架**：Node.js + Express 或 Python Flask（轻量级 API 服务）
- **数据库**：SQLite（V1阶段，数据量小，简单易用）
- **文件存储**：本地磁盘存储图片（可扩展到云存储如 S3/OSS）
- **API 设计**：RESTful API

#### 核心 API 端点
```
POST   /api/collections          - 创建收藏记录
GET    /api/collections           - 获取收藏列表
GET    /api/collections/:id       - 获取单个收藏详情
PUT    /api/collections/:id       - 更新收藏记录
DELETE /api/collections/:id       - 删除收藏记录
POST   /api/collections/:id/image - 上传收藏图片
```

#### 数据库设计

**collections 表**
| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PRIMARY KEY | 唯一标识 |
| title | TEXT | 收藏标题 |
| category | TEXT | 分类 |
| date_acquired | TEXT | 获得日期 |
| location | TEXT | 获得地点 |
| story | TEXT | 收藏故事 |
| image_url | TEXT | 图片路径 |
| tags | TEXT | 标签（JSON 格式） |
| created_at | TEXT | 创建时间 |
| updated_at | TEXT | 更新时间 |

## V1.2：AI 辅助记录

### 产品功能

- AI 根据用户输入生成标题建议
- AI 推荐收藏类别
- AI 推荐标签
- AI 帮用户润色或生成收藏故事
- 用户可以修改所有 AI 生成内容

### 技术路线

#### AI 集成方案

**方案选型**：
- **OpenAI API**（GPT-3.5/GPT-4）：成熟、稳定、效果好
- **Claude API**：Alternative 选择
- **本地模型**：如 Llama2（需考虑部署成本）

**API 设计**：
```
POST /api/ai/suggest-title
POST /api/ai/suggest-category
POST /api/ai/suggest-tags
POST /api/ai/generate-story
```

#### AI 提示词设计要点

**标题生成提示词示例**：
```
你是一个收藏品记录助手。用户正在记录一件收藏品，
请根据以下信息生成一个简洁、有情感色彩的标题建议。

物品类型：{category}
获得地点：{location}
获得时间：{date}
已有描述：{description}

请生成3个不同风格的标题建议，每个不超过20字。
```

**故事生成提示词示例**：
```
你是一个记忆记录助手。用户正在记录一件有个人意义的收藏品。
请根据以下信息，生成一段100-150字的收藏故事或回忆描述。

物品类型：{category}
获得地点：{location}
获得时间：{date}
物品名称：{title}

故事应该温暖、有情感，能唤起美好回忆。
用户可以修改生成的内容。
```

#### AI 服务架构

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   前端 App   │────▶│  API Server  │────▶│  AI API     │
│  (Flutter)  │     │  (Node.js)   │     │ (OpenAI)    │
└─────────────┘     └─────────────┘     └─────────────┘
                          │
                          ▼
                   ┌─────────────┐
                   │  SQLite DB  │
                   └─────────────┘
```

#### 关键实现细节

1. **异步处理**：AI 生成需要时间，使用 loading 状态提示用户
2. **缓存机制**：相同输入的 AI 建议可以缓存，减少 API 调用
3. **降级方案**：AI 服务不可用时，用户仍可手动输入
4. **字数限制**：控制单次 API 处理的文本长度，控制成本

## V1.3：美观收藏卡片墙

### 产品功能

- 收藏以卡片形式展示
- 图片、标题、标签、地点和日期有较好的视觉布局
- 收藏列表看起来像个人展览或数字手账墙
- 整体界面具备审美感和情感氛围

### 技术路线

#### UI/UX 设计要点

1. **卡片设计**：
   - 图片为主视觉，占卡片 60-70%
   - 标题使用衬线字体或手写字体
   - 标签使用胶囊样式
   - 圆角和阴影营造卡片感

2. **色彩方案**：
   - 温暖的米色/奶白色背景
   - 柔和的标签颜色（莫兰迪色系）
   - 可选的深色模式

3. **动效设计**：
   - 卡片加载时的淡入动画
   - 下拉刷新动画
   - 页面切换的过渡动画

#### 前端实现

- **Flutter**：
  - 使用 `flutter_staggered_grid_view` 实现瀑布流布局
  - 使用 `cached_network_image` 缓存图片
  - 使用 `flutter_animate` 添加动画效果

- **React Native**：
  - 使用 `react-native-masonry-list` 或 `FlatList` + 自定义布局
  - 使用 `react-native-fast-image` 优化图片加载

#### 性能优化

1. **图片优化**：
   - 上传时压缩图片（建议 1080p 以内）
   - 使用 WebP 格式（如果支持）
   - 懒加载（Lazy loading）

2. **列表优化**：
   - 分页加载（每页 20 条）
   - 下拉刷新
   - 上拉加载更多

3. **缓存策略**：
   - 本地缓存收藏列表
   - 图片缓存到本地

- 按地点筛选

### 技术路线

#### 搜索实现

**前端**：
- 搜索框组件 + 实时搜索（debounce 300-500ms）
- 筛选器 UI（下拉筛选、多选标签）

**后端**：
```sql
-- 关键词搜索
SELECT * FROM collections
WHERE title LIKE '%keyword%'
   OR story LIKE '%keyword%'
   OR tags LIKE '%keyword%'

-- 分类筛选
SELECT * FROM collections WHERE category = '矿石'

-- 时间排序
SELECT * FROM collections ORDER BY date_acquired DESC
```

#### 筛选器数据结构

```json
{
  "keyword": "矿石",
  "category": "矿石收藏",

  "sortBy": "date_desc"
```

## V1.0 风险清单

### 🔴 高风险

#### 1. AI API 成本不可控
- **描述**：用户量增加后，AI 调用次数会大幅上升，OpenAI API 费用可能成为主要成本
- **影响**：如果免费用户使用频率高，可能导致亏损
- **缓解措施**：
  - 设置免费用户 AI 调用限额（如每天10次）
  - 实施 API 使用量监控和告警
  - 考虑接入多个 AI 提供商（OpenAI / Claude）以便成本优化

#### 2. 图片存储成本
- **描述**：用户上传大量高清图片，本地存储或云存储都会产生成本
- **影响**：存储费用随用户量线性增长
- **缓解措施**：
  - 图片压缩（上传时转码为 1080p 以内）
  - 支持 WebP/HEIF 等高效格式
  - 制定存储收费门槛（免费 1GB，付费扩展）

### 🟡 中风险

#### 3. AI 生成质量不稳定
- **描述**：AI 生成的标题、标签、故事可能不符合用户预期
- **影响**：用户可能觉得 AI 功能"鸡肋"，降低使用意愿
- **缓解措施**：
  - 提供多个建议供选择
  - 所有 AI 内容必须可编辑
  - 持续优化提示词模板
  - 收集用户反馈迭代

#### 4. 首次使用体验复杂
- **描述**：V1.0 功能较多（记录+AI+展示），首次用户可能不知道从何开始
- **影响**：用户可能因为上手困难而流失
- **缓解措施**：
  - 设计新手引导流程
  - 提供示例收藏数据
  - 第一件收藏使用教程

#### 5. SQLite 扩展性限制
- **描述**：SQLite 适合小规模数据，但用户量增加后可能成为瓶颈
- **影响**：查询变慢，功能受限
- **缓解措施**：
  - V1 阶段使用 SQLite 快速验证
  - 预留迁移到 PostgreSQL/MySQL 的方案

### 🟢 低风险

#### 6. 图片上传失败
- **描述**：网络不稳定时图片上传可能中断
- **影响**：用户体验差，可能丢失数据
- **缓解措施**：
  - 实现断点续传
  - 本地先缓存，上传后同步
  - 上传失败重试机制

#### 7. 跨平台兼容问题
- **描述**：Flutter/React Native 在某些机型上可能有兼容问题
- **影响**：特定机型用户无法正常使用
- **缓解措施**：
  - 主要机型测试（iOS 14+, Android 10+）
  - 收集崩溃日志，快速修复

## V1.0 技术选型总结

| 层级 | 技术选型 | 说明 |
|------|----------|------|
| 前端框架 | Flutter | 跨平台，本能原生体验 |
| 后端框架 | Node.js + Express | 轻量，生态成熟 |
| 数据库 | SQLite | 快速验证，后期可迁移 |
| AI 能力 | OpenAI API | GPT-3.5 成本可控 |
| 图片存储 | 本地存储（后期 S3） | 简单，后期扩展 |
| 状态管理 | Riverpod / Provider | Flutter 生态成熟方案 |
